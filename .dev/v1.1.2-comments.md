## Message

Hello, and thank you for the detailed review. Version 1.1.2 addresses every point; the
items where we took a different route than the one suggested are explained below.

**Ajax endpoint URL.** `admin-ajax.php` is no longer hardcoded. The URL comes from
`admin_url( 'admin-ajax.php' )` in PHP and is passed to the script with `wp_localize_script()`
(`pivotPerformanceToolkitAdmin.ajaxUrl`); every AJAX request uses it, and `dist/admin-js.js`
has been rebuilt.

**Generic names and prefixes.** The remaining `ptk` identifiers (JavaScript globals, REST
namespace, drop-in variables, headers, labels) now use `pivot_performance_toolkit`. We removed
the bundled Symfony mbstring and PHP 8.3 polyfills, which were the source of the global
`Date*Exception`, `SQLite3Exception`, `Override` and `mb_*` declarations (the plugin now
requires the PHP mbstring extension and shows an admin notice if it is missing), and the
vendored Composer autoloader classes are renamed to `PivotPerformanceToolkit_Autoloader_*`.

One name cannot be changed: `includes/Cache/object-cache.php` is an object-cache drop-in, and
WordPress requires a drop-in to define a class named `WP_Object_Cache` and the global
`wp_cache_*()` functions under exactly those names. The file is not loaded by the plugin; it is
copied to `wp-content/object-cache.php` only when an administrator enables the file object
cache, and it never overwrites another plugin's drop-in. This is explained at the top of the
file and in a readme FAQ entry.

**Documented source for compressed files.** `dist/admin-js.js` and `dist/admin.css` are built
from `src/js/admin.js` and `src/css/admin.css`. Those sources, `package.json`,
`package-lock.json` and `vite.config.js` are now included in the plugin package and published
in the public repository (https://github.com/pivot-labs/pivot-performance-toolkit, tagged per
release). The readme's "Source Code" section maps each built file to its source and gives the
exact steps (`npm ci`, `npm run build`); we checked that those steps reproduce both shipped
files byte for byte from only the included sources. Everything else (`assets/js`,
`assets/css`, all PHP) ships as written, and the bundled PHP libraries in `includes/Vendor`
are listed in the readme with versions, upstream links and the build-time changes made to them.

**External services.** The flagged `CachePage.php` call is not a third-party service. It is the
cache-preload loopback request: if fetching one of this site's own URLs over HTTPS fails
(self-signed certificates on local servers), the same URL on the same host is retried once over
`http://`. Preloadable URLs are already restricted to the site's own host. The readme's
"External services" section now lists every request the plugin makes to the site's own address
(cache preload, asset detector, HTTP protocol check) and states that, apart from the optional
Cloudflare integration (already documented with service, terms and privacy links), the plugin
contacts no external server. The `symfony/polyfill-php83` hit was a URL in a code comment in a
library that is no longer bundled.

**File and directory locations.** `Menu.php` no longer uses `WP_PLUGIN_DIR`; it uses
`plugin_basename()`. `LocalAssetResolver` and the asset detector no longer assume the URL
mirrors the directory layout: they take their prefixes from `content_url()`, `site_url()`,
`wp_upload_dir()`, `includes_url()`, `get_theme_root_uri()`, `plugins_url()` and `admin_url()`.
The one remaining `WP_CONTENT_DIR . '/object-cache.php'` is required by WordPress itself (an
object-cache drop-in is only loaded from the content directory) and is commented. The
`Stringable.php:261` hit is `dirname()` on a string inside the bundled Illuminate library, not
a plugin location.

**Default timezone.** The only `date_default_timezone_set()` call was in the bundled Carbon
library (its test-time-travel feature, never reached at runtime). Carbon and its dependencies
are no longer bundled, so the call is gone from the package.

**Writing to disallowed locations.** The three flagged writes were the generated minified and
combined CSS/JS files. They are public static assets, so they are now written to
`pivot-performance-toolkit/minified-assets` and `…/combined-assets` inside the uploads
directory, resolved with `wp_upload_dir()` (new class `includes/Utils/AssetStorage.php`), and
the purge actions, status check and uninstall use the same class. What remains in `wp-content`
is the caching-plugin exception you describe: the page cache and its settings file under
`wp-content/cache/pivot-performance-toolkit/` (read by the `advanced-cache.php` drop-in before
WordPress loads, so it cannot depend on uploads or on loading plugin code), the
`advanced-cache.php` / `object-cache.php` drop-ins, and the compiled admin templates in
`wp-content/cache/pivot-performance-toolkit-blade/` (executable PHP, deliberately not placed in
the publicly served uploads folder). Only if an administrator enables the matching option does
the plugin add a `WP_CACHE` line to `wp-config.php` or cache headers to `.htaccess`. Nothing is
written to the plugin folder, other plugins or themes, or core directories, and users never
need to edit plugin files. A readme FAQ entry lists every location.

**wp_enqueue.** Tags that are rewritten in the finished page (inside the
`wp_template_enhancement_output_buffer` filter, after enqueueing is over) are no longer built by
string concatenation. `AsyncCss` rewrites the existing `<link>` with `WP_HTML_Tag_Processor`
(its `<noscript>` fallback is the untouched original tag); `Combine` builds its replacement
`<link>` with the same API and its replacement `<script>` with `wp_get_script_tag()`. In
`advanced-cache.php` the large inline script is gone: for a performance-test request that hits
the page cache, the drop-in now adds one `<script src>` pointing at
`assets/js/performance-probe.js`, the same file the plugin enqueues with `wp_register_script()` /
`wp_enqueue_script()` / `wp_localize_script()` on uncached pages. That one tag is still written
by hand because the drop-in runs from `wp-settings.php` before WordPress, the script loader and
the hook system exist, and the document it changes is a finished HTML file on disk.

**Nonces and permissions.** Every AJAX and `admin-post` action checks a nonce
(`check_ajax_referer()` / `check_admin_referer()`) and `current_user_can( 'manage_options' )`. We
removed the `$_GET` reads that carried notice text and "settings saved" flags: outcomes are now
stored server-side in a one-time, per-user transient, and "settings saved" comes from core's
`get_settings_errors()`. Navigation no longer uses plugin query parameters: each screen is a
registered admin page and the plugin reads the current one from core's `$plugin_page`. The
database table sort links carry a nonce and the sort is applied only when it verifies. The only
`$_GET` read left is the admin-bar purge target, read after `check_admin_referer()`.

**Sanitizing `$_SERVER` and `$_COOKIE`.** Every read now goes through one class,
`includes/Utils/RequestInput.php`, which unslashes and sanitizes before returning a value.
Host and request URI feed the page-cache key, where `sanitize_text_field()` would be wrong (it
strips percent-encoded octets, so `/caf%C3%A9` and `/caf%C3%A8` would share one cache entry),
so those keep printable ASCII and drop control characters, spaces and non-ASCII bytes; they are
only hashed or compared, never output. `advanced-cache.php` is included from `wp-settings.php`
before `wp-includes/formatting.php`, so `sanitize_text_field()` and `wp_unslash()` do not exist
yet; it applies the same filter through one local function, explained in a comment block at the
top of the file. A unit test runs the real drop-in in a separate PHP process and checks it
finds the file `PageCache` wrote for the same request, so the two cannot drift apart.

**Escaping.** The three `wp_add_inline_*` calls are gone: that code now ships as ordinary
enqueued files (`assets/js/delayed-js-runtime.js`, `assets/js/performance-probe.js`,
`assets/css/menu-icon.css`) with their values passed through `wp_localize_script()`. We removed
Composer's PHP < 5.6 error branch from `includes/Vendor/autoload.php` (the plugin requires PHP
8.2), and the settings export no longer echoes a file: it is returned with
`wp_send_json_success()` and saved by the browser. Rendered admin views go through a single
`BladeEngine::display()`, and a PHPUnit test scans every template and fails the build if a value
is printed without escaping. Two `echo` statements remain, each explained in a comment next to
it: `BladeEngine::display()` outputs a template that Blade has already escaped at render time (a
whole admin screen of forms and inline SVG, which `wp_kses_post()` would strip), and
`advanced-cache.php` replays a page we cached earlier before WordPress has loaded, when the
escaping functions do not exist yet; escaping either would corrupt the output.

**Unsafe SQL.** `DatabaseOptimizer::getTableStats()` is now a constant `information_schema`
query with no request-derived value; sorting happens in PHP against a fixed allowlist of
columns. `optimizeTables()` binds the table name with `$wpdb->prepare( 'OPTIMIZE TABLE %i', … )`.
The other queries have no variables or use `$wpdb->prepare()`; the only interpolated values are
core's `$wpdb->posts`, `$wpdb->comments` and `$wpdb->options` table-name properties.

**Unclosed `ob_start()`.** The seven flagged calls are gone. `ManagesStacks`, `ManagesFragments`,
`ManagesLayouts` and `ManagesTranslations` implement `@push`, `@fragment`, `@section` and `@lang`,
which none of the plugin's 92 templates use, so the build removes those traits from the bundled
`illuminate/view`. `ManagesComponents` held a buffer open between the opening and closing tag of
`<x-component>` / `<x-slot>`; the build removes it too, and the plugin renders components with
its own `includes/Views/ClosureComponents.php` and a small compiler subclass that turns each
component and slot body into a closure. `capture()` runs that closure inside `ob_start()` …
`try { } finally { ob_get_clean() }` in a single function, so a buffer is always opened and
closed in the same function scope, even if a template throws. The only `ob_start()` left in the
bundled library is `PhpEngine::evaluatePath()`, which already pairs its own. Tests fail if any
other vendor file starts calling `ob_start()`, and render real components, slots and loops.

We also ran the Plugin Check tool on the built package; it reports no findings.

Thank you again.
