## Ajax endpoint URL

Status: code fixed. **Reply ready.**

What WP.org requires (from their review), and how each point is met:

| WP.org requirement | How the plugin meets it |
|---|---|
| Never assume the endpoint is `wp-admin/admin-ajax.php`; other configurations won't work. | The literal path is gone from `src/js/admin.js` and from the rebuilt `dist/admin-js.js`. |
| Determine the location with a function, e.g. `admin_url( 'admin-ajax.php' )`. | `Menu.php` sets `'ajaxUrl' => admin_url( 'admin-ajax.php' )`. |
| Execute that call in PHP and pass it to the JS with `wp_localize_script()` (also the place for the nonce). | The value is localized on the existing `pivot-performance-toolkit-admin-js` handle, as `pivotPerformanceToolkitAdmin.ajaxUrl`. |
| Refer to the endpoint in the JS through the localized variable. | `getAjaxUrl()` reads `pivotPerformanceToolkitAdmin.ajaxUrl`; all five `fetch()` calls go through one `ajaxFetch()` helper. |

Notes for us (not for the reviewer):

- Nonces: WP.org's example localizes one nonce. We keep a separate nonce per action in
  `data-ajax-nonce` attributes; the requirement is the URL, so this was left as is.
- If `ajaxUrl` is missing, the helper falls back to core's `window.ajaxurl`. If neither
  exists, `ajaxFetch()` rejects, so each caller's existing `.catch` shows "Request failed."
  rather than POSTing to the current page.
- WP.org's example variable `pivopeto-ajax` has a hyphen and isn't a valid JS identifier;
  ours is camelCase.

> **Ajax endpoint.** The admin script no longer hardcodes `/wp-admin/admin-ajax.php`.
> The URL is generated in PHP with `admin_url( 'admin-ajax.php' )` and passed to the

## Sanitize, validate and escape input (`$_SERVER`, `$_COOKIE`)

Status: **fixed.**

Reply (paste-ready):

> - Every `$_SERVER` / `$_COOKIE` read in the plugin now goes through one class, `includes/Utils/RequestInput.php`, which unslashes and sanitizes (`sanitize_text_field( wp_unslash() )`) before returning a value. This replaces the scattered reads in `PageCache.php`, `AdminBarMenu.php`, `HttpProtocolDetector.php`, `SystemStatusPage.php`, `BrowserCacheHeadersPage.php`, `AsyncCss.php`, `Assets.php`, `Combine.php` and `DelayedJs.php`, and the per-line `phpcs:ignore` comments there are gone. Cookie names are sanitized before they are matched against the admin-configured bypass rules.
> - Host and request URI are used to build the page-cache key. `sanitize_text_field()` would be wrong there (it strips percent-encoded octets, so `/caf%C3%A9` and `/caf%C3%A8` would share one cache entry), so `RequestInput::keyPart()` keeps printable ASCII and drops control characters, spaces and raw non-ASCII bytes. The values are only hashed or compared, never echoed.
> - `includes/Cache/advanced-cache.php` is a WordPress drop-in included from `wp-settings.php` before `wp-includes/formatting.php`, so `sanitize_text_field()` and `wp_unslash()` do not exist yet and cannot be loaded early. It applies the same printable-ASCII filter through one local function, with a comment block at the top of the file explaining this. The superglobals have not been slashed yet at that point, so there is nothing to unslash. A unit test runs the real drop-in in a separate PHP process and checks it finds the file `PageCache` wrote for the same request (quotes, backslashes, control characters, percent-encoding, non-ASCII, missing host), so the two cannot drift apart.
> - Remaining `$_GET`/`$_POST` reads were already nonce/capability checked and sanitized (`sanitize_key`, `esc_url_raw`, `sanitize_text_field`).
