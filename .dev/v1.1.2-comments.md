## Message

Hello, and thank you for the detailed review. Version 1.1.2 addresses every point. Where we
took a different route than the one suggested, it is explained below.

**Ajax endpoint URL.** The URL now comes from `admin_url( 'admin-ajax.php' )` and is passed
to the script with `wp_localize_script()` (`pivotPerformanceToolkitAdmin.ajaxUrl`); the hardcoded
path is gone and `dist/admin-js.js` is rebuilt.

**Generic names and prefixes.** All remaining `ptk` identifiers now use `pivot_performance_toolkit`.
We removed the bundled Symfony mbstring and PHP 8.3 polyfills (the source of the global
`Date*Exception`, `SQLite3Exception`, `Override` and `mb_*` declarations); the plugin now
requires the PHP mbstring extension and shows an admin notice if it is missing. The vendored
Composer autoloader classes are renamed to `PivotPerformanceToolkit_Autoloader_*`.

One name cannot change: `includes/Cache/object-cache.php` is an object-cache drop-in, and
WordPress requires a drop-in to define `WP_Object_Cache` and the global `wp_cache_*()`
functions under exactly those names. The plugin never loads that file; it is copied to
`wp-content/object-cache.php` only when an administrator enables the file object cache, and
it never overwrites another plugin's drop-in. This is explained in the file and in a readme FAQ.

**Documented source for compressed files.** `dist/admin-js.js` and `dist/admin.css` are built
from `src/js/admin.js` and `src/css/admin.css`. Those sources, `package.json`,
`package-lock.json` and `vite.config.js` now ship in the plugin package and are published in
the public repository (https://github.com/pivot-labs/pivot-performance-toolkit, tagged per
release). The readme's "Source Code" section maps each built file to its source and gives the
steps (`npm ci`, `npm run build`); we verified they reproduce both shipped files byte for byte
from only the included sources. All other JS, CSS and PHP ships as written, and the bundled
libraries in `includes/Vendor` are listed in the readme with versions, upstream links and the
build-time changes made to them.

**External services.** The flagged `CachePage.php` call is not a third-party service: it is the
cache-preload loopback request. If fetching one of this site's own URLs over HTTPS fails
(self-signed certificates on local servers), the same URL on the same host is retried once over
`http://`. The readme's "External services" section now lists every request the plugin makes to
the site's own address (cache preload, asset detector, HTTP protocol check) and states that,
apart from the optional Cloudflare integration (documented with service, terms and privacy
links), the plugin contacts no external server. The `symfony/polyfill-php83` hit was a URL in a
comment in a library that is no longer bundled.

**File and directory locations.** `Menu.php` uses `plugin_basename()` instead of
`WP_PLUGIN_DIR`. The asset resolver and detector take their URL prefixes from `content_url()`,
`site_url()`, `wp_upload_dir()`, `includes_url()`, `get_theme_root_uri()`, `plugins_url()` and
`admin_url()` instead of assuming the URL mirrors the directory layout. The one remaining
`WP_CONTENT_DIR . '/object-cache.php'` is required by WordPress (a drop-in loads only from the
content directory) and is commented. The `Stringable.php` hit is `dirname()` on a string inside
the bundled Illuminate library, not a plugin location.

**Default timezone.** The only `date_default_timezone_set()` call was in the bundled Carbon
library (test-time-travel code, never reached at runtime). Carbon is no longer bundled.

**Writing to disallowed locations.** The three flagged writes were the generated minified and
combined CSS/JS files. They are now written to `pivot-performance-toolkit/minified-assets` and
`…/combined-assets` inside the uploads directory, resolved with `wp_upload_dir()` (new class
`includes/Utils/AssetStorage.php`); the purge actions, status check and uninstall use the same
class. What remains in `wp-content` is the caching-plugin exception you describe: the page cache
and its settings file under `wp-content/cache/pivot-performance-toolkit/` (read by the
`advanced-cache.php` drop-in before WordPress loads, so it cannot depend on uploads or plugin
code), the `advanced-cache.php` / `object-cache.php` drop-ins, and the compiled admin templates in
`wp-content/cache/pivot-performance-toolkit-blade/` (executable PHP, deliberately not placed in the
publicly served uploads folder). Only if an administrator enables the matching option does the
plugin add a `WP_CACHE` line to `wp-config.php` or cache headers to `.htaccess`. Nothing is
written to the plugin folder, other plugins or themes, or core, and users never need to edit
plugin files. A readme FAQ lists every location.

**wp_enqueue.** Tags rewritten in the finished page (inside the
`wp_template_enhancement_output_buffer` filter, after enqueueing is over) are no longer built by
string concatenation. `AsyncCss` rewrites the existing `<link>` with `WP_HTML_Tag_Processor`;
`Combine` builds its `<link>` with the same API and its `<script>` with `wp_get_script_tag()`. In
`advanced-cache.php` the large inline script is gone: for a performance-test request that hits
the page cache, the drop-in now adds a single `<script src>` for `assets/js/performance-probe.js`,
the same file the plugin enqueues with `wp_register_script()` / `wp_enqueue_script()` /
`wp_localize_script()` on uncached pages. That one tag is still written by hand because the
drop-in runs from `wp-settings.php`, before WordPress, the script loader and the hook system
exist, and the document it changes is a finished HTML file on disk.

**Nonces and permissions.** Every AJAX and `admin-post` action checks a nonce
(`check_ajax_referer()` / `check_admin_referer()`) and `current_user_can( 'manage_options' )`.
The `$_GET` reads that carried notice text and "settings saved" flags are gone: outcomes are
stored server-side in a one-time, per-user transient, and "settings saved" comes from core's
`get_settings_errors()`. Navigation no longer uses plugin query parameters: each screen is a
registered admin page and the plugin reads the current one from core's `$plugin_page`. Two
`$_GET` reads remain, both behind a nonce check: the database table sort links (applied only
when the nonce verifies) and the admin-bar purge target.

**Sanitizing `$_SERVER` and `$_COOKIE`.** Every read goes through one class,
`includes/Utils/RequestInput.php`, which unslashes and sanitizes before returning a value. Host
and request URI feed the page-cache key, where `sanitize_text_field()` would be wrong (it strips
percent-encoded octets, so `/caf%C3%A9` and `/caf%C3%A8` would share a cache entry); those keep
printable ASCII and drop control characters, spaces and non-ASCII bytes, and are only hashed or
compared, never output. `advanced-cache.php` runs before `wp-includes/formatting.php` is loaded,
so `sanitize_text_field()` and `wp_unslash()` do not exist yet; it applies the same filter through
one local function, explained in a comment at the top of the file. A unit test runs the real
drop-in in a separate PHP process and checks it finds the file `PageCache` wrote for the same
request, so the two cannot drift apart.

**Escaping.** The `wp_add_inline_*` calls you listed are gone: that code now ships as enqueued
files (`assets/js/delayed-js-runtime.js`, `assets/js/performance-probe.js`,
`assets/css/menu-icon.css`) with values passed through `wp_localize_script()`. (The admin-bar
indicator still uses `wp_add_inline_style()` on a registered handle, with a fixed string and no
variable input.) Composer's PHP < 5.6 error branch is removed from `includes/Vendor/autoload.php`,
and the settings export no longer echoes a file: it is returned with `wp_send_json_success()` and
saved by the browser. Rendered admin views go through a single `BladeEngine::display()`, and a
PHPUnit test scans every template and fails if a value is printed without escaping. Two `echo`
statements output pre-built markup and cannot be escaped further, each explained in a comment:
`BladeEngine::display()` outputs a template Blade already escaped at render time (a whole admin
screen of forms and inline SVG, which `wp_kses_post()` would strip), and `advanced-cache.php`
replays a page we cached earlier before WordPress has loaded, when the escaping functions do not
exist yet.

**Unsafe SQL.** `DatabaseOptimizer::getTableStats()` is now a constant `information_schema`
query with no request-derived value; sorting happens in PHP against a fixed allowlist.
`optimizeTables()` uses `$wpdb->prepare( 'OPTIMIZE TABLE %i', … )`. The other queries have no
variables or use `$wpdb->prepare()`; the only interpolated values are core's `$wpdb->posts`,
`$wpdb->comments` and `$wpdb->options` table names.

**Unclosed `ob_start()`.** The seven flagged calls are gone. `ManagesStacks`, `ManagesFragments`,
`ManagesLayouts` and `ManagesTranslations` implement `@push`, `@fragment`, `@section` and `@lang`,
which none of the plugin's 92 templates use, so the build removes those traits from the bundled
`illuminate/view`. `ManagesComponents` held a buffer open between the opening and closing tag of
`<x-component>` / `<x-slot>`; the build removes it too, and the plugin renders components with
its own `includes/Views/ClosureComponents.php`, which compiles each component and slot body into a
closure. `capture()` runs that closure inside `ob_start()` … `try { } finally { ob_get_clean() }`
in a single function, so a buffer is always opened and closed in the same scope, even if a
template throws. The only other `ob_start()` in the bundled library is `PhpEngine::evaluatePath()`,
which already pairs its own. Tests fail if any other vendor file starts calling `ob_start()`, and
they render real components, slots and loops.

We also ran Plugin Check on the built package; it reports no findings. Thank you again.
